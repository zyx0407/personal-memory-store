TRIGGERS · ENTRY
One conversation turn
Questions / corrections / follow-ups; read the core first, then shards on demand
End-of-turn check
Semi-automatic extraction → candidate list; write only after confirmation
Verify & troubleshoot
"What is it / how many / which date / which version" → look it up first
Resolve conflicts on the spot
FOUR LAYERS · ONE WRITER
Core · MEMORY.md (always injected)
Identity · preferences · stable rules · pointers; ≤10KB
Injected every turn, not "remembered" by the model
Shards · memory/*.md (read on demand)
Topic facts; the index decides which shard to read; never injected
Current values live only in shards; if missing, say "not in the store"
Timeline
Change log = one line per day (only what changed)
Stream = per-turn process (recent window only, older compressed by day)
Derived layer (rebuildable, never the truth)
Checks · index/search · evals · candidate list
Numbers are computed at runtime, never hard-coded
WRITE · READ · DISTILL
Three write gates
① Entry filter: only identity / preferences / stable rules / long-term goals reach the core
② Recency: newer date wins; mark the old line superseded
③ Merge on write: candidate carries "merge → shard#item"
Three read checks
① Check before answering: search or read the shard first
② Compute numbers: sizes/counts/headroom are never hard-coded
③ Provenance: every entry is traceable
Distill
Stream → candidate draft → confirmation → write core/shard
No confirmation = rejected; the original stays in the stream
RED LINES · HEALTH · BOUNDARIES
Red lines (hard limits)
Core ≤10KB · shard ≤12KB · whole store ≤400KB
Change log ≤50KB · stream ≤120KB
Archive, don't delete · pointers stay inside · one writer
Health check (before changing the store)
ERROR / WARN · broken links · conflicts · stale dates · duplicates
Budget headroom · provenance coverage · draft backlog
ERROR must be zero before writing
Boundaries (2026-11)
Single user · plain text · one writer
